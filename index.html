Which Pages to Fix First: A Content Refresh Scoring Model

By J. Aamir · Repository on GitHub

Abstract

A company with thousands of web pages can only afford to review a small number each week, so the real question is which pages to look at first. We built a model that ranks pages by how likely they are to be losing search visibility, using a public starter dataset of 30,000 anonymized pages across 32 clients. We compared a simple hand written rule against a Random Forest classifier, tested honestly on clients the model had never seen during training. The model reached a Precision at 50 of 0.74, compared to 0.58 for the rule, meaning that out of the top 50 flagged pages, about 37 were genuinely declining instead of about 29. We report this as a decision support tool for a human editor, not a guarantee, and we show exactly where the model gets things wrong.

Introduction

SEO teams manage far more pages than they can personally review. A page that was written well a year ago can quietly lose visitors as competitors publish newer content, as Google changes how it ranks results, or as a page simply goes stale. The team that owns these pages usually has the resources to refresh maybe twenty to fifty pages a week, so the actual decision they face every week is not "is this page good or bad," it is "which pages do we touch first."

Right now this decision is often made with a hand written rule, something like "flag any page that has not been updated in six months and still gets meaningful traffic." We tested that kind of rule directly on real data and found it only flagged 17 pages out of 30,000, far too narrow a list for a real editorial team to work from. This paper asks whether a trained model, built honestly and validated carefully, can do better than that rule without quietly cheating in the process.

Data

We used the starter release from the FlyRank ML Internship dataset: 30,000 anonymized content pages across 32 clients, each with 44 columns of trailing 90 day search and analytics metrics. Every page and client identifier is pseudonymized. No client names, URLs, or private queries appear anywhere in this paper or in the underlying notebooks.

We also had access to a larger hosted warehouse release with close to 79 million daily rows, which we queried directly for an earlier data contract exercise, but the model in this paper is trained and validated on the 30,000 row starter release for consistency across our weekly checkpoints.

What we excluded, and why

  • trend_direction and trend_pct: these columns define our label. Including them as features would let the model simply look up the answer instead of predicting it.
  • Rows where avg_position equals zero: in this dataset a zero means no ranking data was recorded, not that the page ranked first. We filtered these out of any position based calculation.
  • Any client or page identifying text: all analysis uses the pseudonymized IDs only.

Methodology

The label

We defined a page as declining if its impressions fell by 20 percent or more compared to the prior 30 day window, which matches the dataset's own trend_direction field. This is a proxy built from a current window comparison, not an independently measured future outcome, and we are careful to describe it that way throughout.

The baseline

Our baseline is a simple rule: flag a page if its click through rate falls meaningfully below the average click through rate for other pages ranking at a similar position, weighted by how many impressions that page already gets. We call this reason code ctr_below_position_benchmark, and the suggested action is to review the page's title and meta description.

The model

We trained a Random Forest classifier on seven features that are all knowable before the fact: content age, days since the last update, impressions, average position, click through rate, word count, and search volume. We deliberately left out anything derived from the label itself.

Validation design

We split the data by client rather than by row, so that no client's pages appear in both the training set and the test set. This matters a great deal. When we tested the same model under a naive row random split, where clients leaked freely between train and test, Precision at 50 looked artificially high at 0.92. Once we corrected the split so that 31 of 32 clients no longer overlapped between train and test, the honest number dropped to 0.74. We report only the client grouped number in our results.

Leakage check

We confirmed that none of our seven features overlap with the two columns that define the label, and we checked that no single feature carries a suspiciously high correlation with the label that would suggest a hidden shortcut. None did.

Where the model gets it wrong

Looking at the model's actual top 20 picks on held out data, every single false positive was a young page currently labeled stable, not declining. The two features the model leans on most are content age and impressions, and it appears to over apply the general pattern that younger pages decline more often, flagging some young pages that have not actually started declining yet. This is a real and specific weakness, not just a number on a chart.

Limitations and honest framing

  • This is an observational, correlational study. Nothing here proves that refreshing a page causes it to recover, only that certain page characteristics are associated with decline in this dataset.
  • The label is a proxy built from a 30 day impressions comparison, not a verified future outcome. A page labeled declining today could recover on its own regardless of any action taken.
  • The model was trained and validated on 32 clients. We have not tested how it performs on a brand new client or a different industry, and we would expect some drop in accuracy there until it is retrained or revalidated.
  • A Precision at 50 of 0.74 means roughly one in four of the top flagged pages will not actually be declining. This is a decision support signal for a human reviewer, not an automated judgment.

Ranked recommendations

Our action playbook maps each page to one of four reason codes.

1. High decline risk and CTR gap — refresh the content and review the title and snippet together. These pages carry both a model flagged decline risk and a click through rate well below what similar pages earn.
2. High decline risk only — refresh the content. Click performance is fine, but the broader pattern suggests the page is losing ground.
3. CTR gap only — review the title and meta description. Decline risk is low, but the page is underperforming for its search position.
4. Low priority — monitor only, no action needed this cycle.

A human should always check the underlying numbers for a flagged page before acting, and nothing here should be used to judge an individual writer or editor's performance.
